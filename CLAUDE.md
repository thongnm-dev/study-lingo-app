## What this is

A mobile app for learning **English and Japanese**. The two languages are first-class peers, not an afterthought — design every feature (vocabulary, lessons, quizzes, audio, writing practice) to work for both, and assume Japanese-specific concerns from day one: kanji/kana rendering, furigana, JLPT levels, and stroke order. The UI goal is a polished, "smooth" Material experience (Material 3, deliberate motion/transitions, no janky frames).

## Stack

- **Flutter** 3.41.x / **Dart** 3.11.x (stable channel, already installed — no fvm).
- **State management: BLoC** (`flutter_bloc` + `bloc`). This is a hard constraint — do not introduce Provider/Riverpod/GetX/setState-driven state for business logic. Widgets stay dumb; all logic lives in Blocs/Cubits, and Blocs/Cubits only talk to **use cases** (never repositories directly).
- **Dependency injection: `get_it`** (`lib/config/di/service_locator.dart`). Everything cross-cutting — `DioClient`, data sources, repositories, use cases, blocs — is registered here. Do **not** introduce `MultiRepositoryProvider` or other DI mechanisms.
- **Navigation: `go_router`** (`lib/config/router/app_router.dart` + `route_names.dart`). Page-to-page navigation is `context.push(RouteNames.x, extra: …)` / `context.go(...)`; do not add `Navigator.push(MaterialPageRoute(...))` calls.
- **Functional error handling: `dartz`** — use cases return `Either<Failure, T>` (or `Either<Failure, Stream<T>>` for the stream watcher). Blocs `result.fold(...)` to emit success/failure states.
- **HTTP client: `dio`** (`DioClient` in `core/network/`, registered as a lazy singleton). Live data sources go through it; in-memory stubs ignore it.
- **Form validation: `formz`** (added; not yet adopted in code — use it when writing new form fields rather than ad-hoc validation).
- **Material 3** (`useMaterial3: true`) for UI.

## Architecture

Organized **feature-first**, with each feature a self-contained Clean Architecture slice (`domain/` → pure Dart entities + repository interfaces + **use cases**; `data/` → data sources + repository implementations; `presentation/` → bloc/cubit + pages + widgets). The `vocabulary` and `lessons` features are the live references — mirror their layering when adding a feature.

```
lib/
  main.dart                          # Bloc.observer; setupServiceLocator(); runApp(StudyLingoApp())
  app/
    app.dart                         # MaterialApp.router (theme, locale, AppBlocProviders, routerConfig)
    main_shell.dart                  # StatefulNavigationShell consumer (3-tab indexed stack + More action)
  core/
    bloc/app_bloc_observer.dart      # logs Bloc transitions/errors in debug
    constants/                       # app_constants.dart, colors.dart
    exceptions/app_exceptions.dart   # AppException + ServerException / NetworkException / ValidationException
    icons/app_icons.dart             # platform-neutral icon set (PhosphorIcons)
    network/dio_client.dart          # singleton Dio + logging interceptor (used by future live data sources)
    session/current_user.dart        # mutable AuthUser? holder; auth flow writes, router redirect reads
    theme/app_theme.dart             # AppTheme.light()/dark() — Material 3, seed color, smooth page transitions
    usecases/usecase.dart            # `UseCase<T, P>` / `StreamUseCase<T, P>` base classes + NoParams
    utils/failure.dart               # Failure (abstract) + ServerFailure / NetworkFailure / ValidationFailure / UnknownFailure
  config/
    di/service_locator.dart          # GetIt: registers DioClient, data sources, repos, all use cases, every Bloc/Cubit
    provider/bloc_providers.dart     # AppBlocProviders.providers — app-wide LocaleCubit + LanguageCubit (BlocProvider.value)
    router/
      route_names.dart               # String path constants — single source of truth for routes
      app_router.dart                # GoRouter: auth gate via redirect, StatefulShellRoute for tabs, typed extra args
  shared/widgets/                    # Cross-feature widgets (ErrorRetryView, UnsavedChangesGuard)
  features/
    auth/                            # single-screen login/register + Google/Facebook + ForgotPassword (Fake repos)
    kanji/                           # Japanese-only kanji study
    lessons/                         # Topic → Lesson → QuizQuestion; TopicsCubit/LessonsCubit (load) + QuizBloc (run quiz)
    more/                            # the "•••" modal sheet (action, not a tab)
    profile/                         # Hồ sơ screen + DailyProgress entity + ProgressRepository (singleton) + WatchProgressUseCase; ProfileStatsCubit derives streak + lifetime totals
    reminders/                       # ReminderSettings; load + (save+sync) use cases; RemindersCubit
    settings/                        # Settings hub + LocaleCubit (display-language)
    vocabulary/                      # VocabularyWord (EN/JA + target + furigana + JLPT); VocabularyBloc + session-language & JLPT filters
    writing/                         # Hiragana/Katakana/Kanji tracing + stroke-order overlay
```

The dependency direction is enforced and one-way: `presentation` → `domain` ← `data`. Blocs/Cubits depend on **use cases** (from `domain/usecases/`), use cases depend on **repository interfaces** (from `domain/repositories/`), and repository implementations live in `data/`. Swapping an in-memory stub for a real API/sqlite source touches only the data layer + the registration in `service_locator.dart`. Tests under `test/features/<feature>/` mock the use cases (not the repository) with `mocktail` and drive the Bloc/Cubit with `bloc_test`.

**Cubit vs Bloc here** (illustrating the guideline below): simple "load a list / hold settings" units are Cubits (`TopicsCubit`, `LessonsCubit`, `RemindersCubit`, `KanjiListCubit`, `WritingPracticeCubit`, `ProfileStatsCubit`, `LocaleCubit`, `LanguageCubit`) with their `State` class inline in the same file. Event-driven units with several distinct triggers are Blocs (`QuizBloc`, `AuthBloc`, `ForgotPasswordBloc`, `VocabularyBloc`) with `_event.dart`/`_state.dart` `part` files. State is always one immutable class with `copyWith` and a status enum; the UI switches on `status`. **Both kinds live in `presentation/bloc/`** — there is no separate `presentation/cubit/` directory.

### Dependency injection (GetIt)

Every cross-cutting service is registered in `lib/config/di/service_locator.dart` and resolved with `getIt<T>()` at the call site (typically inside a page's `BlocProvider(create: …)` lambda). The file is grouped into:

1. **Session** — `CurrentUser` (lazy singleton holding the signed-in `AuthUser?`).
2. **Network** — `DioClient` (lazy singleton, base URL from `AppConstants`).
3. **Data sources** — lazy singletons (`InMemoryLessonsDataSource`, `InMemoryVocabularyDataSource`).
4. **Repositories** — **lazy singletons (not factories)**. Some hold shared in-memory state, and the single `ProgressRepository` instance (lives under `features/profile/`) is what keeps the quiz writer and the profile-stats reader in sync via its `watch()` stream. Treat that constraint as load-bearing — never register repositories as factories.
5. **Use cases** — `registerFactory` (cheap, stateless wrappers).
6. **App-wide Blocs** — `LocaleCubit` + `LanguageCubit` as `registerLazySingleton`. `LocaleCubit`'s registration calls `..load()` so the saved display language is restored on first access.
7. **Page-scoped Blocs/Cubits** — `registerFactory` (new instance per page). `QuizBloc` uses `registerFactoryParam<QuizBloc, Lesson, void>` because it binds to a specific lesson — resolve it with `getIt<QuizBloc>(param1: lesson)`.

When adding a service, register it in this file and **never** read it from a `RepositoryProvider`/`MultiRepositoryProvider`. Pages provide their own blocs with `BlocProvider(create: (_) => getIt<XBloc>())`.

### Routing (GoRouter)

`lib/config/router/app_router.dart` is the single source of truth for navigation; `route_names.dart` holds the path string constants. The router has:

- An **auth gate via `redirect`**: when `getIt<CurrentUser>().value` is null and the current location is not `/auth` or `/auth/forgot`, redirect to `/auth`. When the user is signed in but lands on `/auth`, redirect to `/home/overview`.
- A **`StatefulShellRoute.indexedStack`** at `/home/{overview,progress,vocabulary}` — `MainShell` consumes the `StatefulNavigationShell` so each tab keeps its own navigation stack and scroll position across switches.
- Page routes for everything else (`/topics`, `/lessons`, `/quiz`, `/practice`, `/profile`, `/settings`, `/settings/language`, `/settings/placeholder`, `/reminders`, `/writing`, `/writing/tracing`, `/kanji`, `/kanji/detail`, `/more`). Routes that need arguments use typed `extra` payloads — see `TopicsPageArgs`, `LessonsPageArgs`, `QuizPageArgs`, `CharacterTracingArgs`, `SettingsPlaceholderArgs` in `app_router.dart`. The receiving builder casts `state.extra!` to the expected type.

Use `context.push(RouteNames.x, extra: Args(...))` from any tap handler. For "replace + clear stack" (e.g. logout) call `context.go(RouteNames.auth)`. The modal More menu still calls `Navigator.pop(entry)` on its `ListTile` (a modal sheet has its own Navigator that GoRouter doesn't manage — that's fine).

### Use cases + Either<Failure, T>

Every public repository method is wrapped in a use case under `<feature>/domain/usecases/` (e.g. `FetchKanjiListUseCase`, `SignInWithEmailUseCase`, `WatchProgressUseCase`, `RecordLessonCompletedUseCase`). Use cases:

- Extend `UseCase<T, P>` from `core/usecases/usecase.dart` (or `StreamUseCase<T, P>` for the stream watcher).
- Take a `Params` value (or `NoParams`); compound inputs live in a dedicated `…Params` `Equatable` class next to the use case.
- Convert exceptions into a `Failure` (`AuthException` → `ValidationFailure`; anything else → `UnknownFailure`).
- Return `Future<Either<Failure, T>>` (or `Either<Failure, Stream<T>>` for `StreamUseCase`).

Blocs invoke a use case and `result.fold((failure) => …, (value) => …)` to emit the right state — they no longer `try/catch` around the repository directly. When wiring a Bloc with multiple use cases, use **named** constructor parameters (see `AuthBloc`, `ForgotPasswordBloc`, `LocaleCubit`, `RemindersCubit`).

### Cross-feature wiring

There is no app-root `MultiRepositoryProvider` — shared services flow through GetIt. The integration points to be aware of:

- **`ProgressRepository` is a singleton** in GetIt, registered from `features/profile/data/`. The reader and writer live in different features but share the same instance: `QuizBloc` finishes → `RecordLessonCompletedUseCase` (`features/quiz/domain/usecases/`) writes to it; `ProfileStatsCubit` subscribes via `WatchProgressUseCase` (`features/profile/domain/usecases/`). The quiz use case imports the `ProgressRepository` interface from `profile/domain/repositories/` — that's the single cross-feature dependency, and it's the price for keeping profile stats and quiz writes in sync. When adding a feature that must react to another's events, share state through a singleton repository like this rather than coupling Blocs directly.
- **`LanguageCubit` is an app-wide singleton** (the *learning-session* language). The vocabulary deck filter follows it: `VocabularyPage`'s initial load reads `context.read<LanguageCubit>().state`, and a `BlocListener` re-requests on session changes. The overview page (Lessons tab) is what mutates it.
- **`CurrentUser` is an app-wide singleton** holding `AuthUser?`. The auth flow writes it on success; the router redirect reads it to gate `/home/*`; pages that need the user (`ProfilePage`, `MainShell`) read it from GetIt. When you lift this into a proper `AuthSessionCubit` later, replace the writes and reads — the rest of the app doesn't care.

### Lessons / quiz specifics

Lessons-tab flow: **an Overview dashboard → pick a skill → topics list → lessons → quiz**. The first tab is `OverviewPage` (`lessons/.../pages/overview_page.dart`), labelled **"Tổng quan" / Overview** (`navLessons` in the ARB files; home icon). It's a single scrolling dashboard styled after a modern course-app home: a gradient **promo banner** ("Luyện tập ngay" → `context.push(RouteNames.practice)`), a **"Chọn ngôn ngữ"** chip row (the two `LearningLanguage`s as flag chips), and a **skill-card grid**. It reads the app-wide `LanguageCubit` (nullable `LearningLanguage`): tapping a language chip calls `LanguageCubit.select(...)` (highlighting it + re-filtering vocabulary) and reveals that language's skills below; until one is picked the skills section shows a "choose a language" hint. The five skills are the `LearningSkill` enum — Ngữ pháp / Từ vựng / Nghe nói / Đọc / Viết (pure-Dart, carries a Vietnamese `label` + `emoji`); each renders as a colored card. Tapping a skill card calls `context.push(RouteNames.topics, extra: TopicsPageArgs(language, skill))`, which loads that skill's topics via `FetchTopicsUseCase` (each `Topic` carries a `skill`) as a **vertical `ListView`**. Tapping a topic pushes `RouteNames.lessons` with `LessonsPageArgs(topic, language)`; tapping a lesson pushes `RouteNames.quiz` with `QuizPageArgs(lesson, lessonTitle)`. `Topic`/`Lesson` expose `titleIn(language)` / `subtitleIn(language)` so the target language is the primary line and the other the secondary. The session is still in-memory — persist via a repository if it should survive restarts.

### Vocabulary (session-filtered deck)

Each `VocabularyWord` carries a `target: LearningLanguage` (imported from lessons' domain — the shared, pure-Dart language enum) marking which study deck it belongs to; JLPT/furigana/romaji stay Japanese-deck-only. `FetchVocabularyWordsUseCase` (with `FetchVocabularyWordsParams(language, jlptLevel)`) filters on both. The list follows the learning session: `VocabularyPage`'s initial load reads the app-wide `LanguageCubit` and a `BlocListener` re-requests on session changes (the tab stays alive in the `StatefulNavigationShell`, so switching language in the Lessons tab re-filters Words live). UI: an active session shows a "Đang học: …" chip; the JLPT chip row is hidden for an English session (JLPT is Japanese-only, and the listener also drops the level filter when switching to English); no session (`null`) shows both decks. `VocabularyCard` renders the `target` language as its primary line (JA: furigana-over-kanji; EN: English headline) with the other language as the gloss, target-language example first. Vocabulary's chrome strings are already migrated to the ARB files.

### Writing practice (Japanese only)

In the Japanese **Viết** skill, `TopicsPage` prepends two cards (shown only when `language == japanese && skill == writing`): **"Luyện viết chữ"** → `context.push(RouteNames.writingHome)`, and **"Học Hán tự"** → `context.push(RouteNames.kanjiList)`.

- **writing**: `WritingHomePage` (pick Hiragana / Katakana / Kanji — full gojūon tables in `InMemoryWritingRepository`) → push `RouteNames.characterTracing` with `CharacterTracingArgs(script: ...)`. Tracing shows the character as a faint guide on a `TracingCanvas` (`CustomPaint` + `GestureDetector` capturing finger strokes). `WritingPracticeCubit` (driven by `FetchWritingCharactersUseCase`) owns the character list + current index; the **drawn strokes are deliberately local widget state** in `_TracingView` (high-frequency pointer data doesn't belong in a Cubit), cleared via a `BlocConsumer.listener` when the index changes. The route also accepts an explicit `characters` list (used to trace a single kanji from its detail page) instead of a `script`.
- **stroke order**: `stroke_order_data.dart` holds hand-approximated, normalized (0..1) stroke polylines keyed by glyph for a representative subset (numbers/simple kanji + simple kana — not the full tables). When `strokeOrderFor(glyph)` is non-null, the tracing screen shows a "Thứ tự nét" button opening `StrokeOrderView`, which animates strokes in order with numbered start points. Absent glyphs simply have no button.
- **kanji**: `KanjiListPage` (grid, `KanjiListCubit` + `FetchKanjiListUseCase` over `InMemoryKanjiRepository`, ~12 N5 kanji) → push `RouteNames.kanjiDetail` with the `Kanji` as `extra` → `KanjiDetailPage` (meaning, on'yomi/kun'yomi, example word, and a "Luyện viết chữ này" button that pushes `RouteNames.characterTracing` with `CharacterTracingArgs(characters: [theKanji])`).

`QuizBloc` is seeded with a `Lesson` (via `getIt<QuizBloc>(param1: lesson)`) and a `RecordLessonCompletedUseCase`, then walks its `questions` one at a time: `QuizAnswerSelected` locks the choice and tallies correctness; `QuizAdvanced` moves on or, on the last question, flips `status` to `finished` and calls the record use case (XP = correct × `Lesson.xpPerCorrectAnswer`). Quiz content is bilingual seed data in `lessons/data/datasources/` — `seedTopics` + per-direction `_japaneseTargetLessons` / `_englishTargetLessons` (selected by `LearningLanguage`).

The More menu's **"Luyện tập"** entry reuses this same flow: `PracticePage` lets the user pick a language, then `getIt<LessonsRepository>().fetchPracticeLesson(language)` builds a synthetic "practice" `Lesson` (breadth-first mix across topics, capped at 8 questions) that runs through the ordinary `QuizBloc`/`QuizPage` — so finishing a practice session records daily progress too.

### Profile (Hồ sơ) + the signed-in user

The authenticated `AuthUser` lives in `getIt<CurrentUser>()`. On login `AuthPage`'s `BlocListener` writes `state.user` into it and calls `context.go(RouteNames.overview)`; the router redirect then allows `/home/*`. `MainShell` reads the user from `CurrentUser` to thread it into `showMoreMenu(context, user)`, which pushes `RouteNames.profile` with the user as `extra`. `ProfilePage` shows identity (avatar/initials, name, email, provider) and lifetime stats via `ProfileStatsCubit`, which subscribes through `WatchProgressUseCase` (totals + streak); its app-bar gear pushes `RouteNames.settings`. Sign-out lives in Settings ("Đăng xuất" → clear `CurrentUser` + `context.go(RouteNames.auth)`, and the router redirect prevents anyone from re-entering `/home/*`). If you lift auth to a proper `AuthSessionCubit` later, replace the `CurrentUser` reads/writes. The `more` and `settings` features are navigation hubs — they push sibling features' routes by design.

### Auth specifics

`AuthBloc` holds the whole login/register form in one immutable state (`email`, `password`, `confirmPassword`, `mode`, `status`) and exposes derived getters (`isEmailValid`, `canSubmit`, …) instead of duplicating validation in the UI. `TextField`s push `*Changed` events on every keystroke; the submit button reads `state.canSubmit`. The bloc takes **five use cases** by name (`signInWithEmail`, `signUpWithEmail`, `signInWithGoogle`, `signInWithFacebook`, `signOut`) — Google/Facebook are just more events (`AuthGooglePressed`/`AuthFacebookPressed`) that funnel through the same `_run` helper as email submit.

`ForgotPasswordBloc` drives the three-step password recovery flow (request → verify → reset) using `RequestOtpUseCase` / `VerifyOtpUseCase` / `ResetPasswordUseCase`. The shared `_run<T>` helper flips to submitting, calls the use case, and on `Right` applies an `onSuccess` mapping; on `Left` it emits a failure with the failure's message.

**Going live (replacing the stubs):** `FakeAuthRepository` and `FakePasswordResetRepository` are simulated backends so the flow runs with zero config. To use real providers, write classes implementing `AuthRepository` and `PasswordResetRepository` (typically `firebase_auth` + `google_sign_in` + `flutter_facebook_auth`) and swap them in `service_locator.dart` — no use-case/Bloc/UI changes needed. Each real provider also needs platform setup (`google-services.json` / iOS `Info.plist` URL schemes, Facebook App ID, OAuth client IDs). The fake has two built-in failure triggers for exercising the error path: email `taken@example.com` (sign-up) and password `wrong` (sign-in).

### Reminders specifics

`RemindersCubit` mutates `ReminderSettings`, and every change is funneled through `SaveReminderSettingsUseCase`, which both persists (via `ReminderRepository.save`) and re-syncs OS notifications (via `ReminderScheduler.sync`). Both backends are stubs today: `InMemoryReminderRepository` (not persisted across restarts) and `LoggingReminderScheduler` (logs instead of firing). **Going live:** back the repository with `shared_preferences`, and implement `ReminderScheduler` with `flutter_local_notifications` + `timezone` (weekly `zonedSchedule` per selected weekday; Android channel + POST_NOTIFICATIONS, iOS permission). `weekdays` follows Dart's `DateTime.monday..sunday` (1–7). Swap both in `service_locator.dart` — no UI/Bloc/use-case changes.

BLoC + Clean Architecture rules to keep the codebase coherent as it grows:
- **One Bloc/Cubit per coherent unit of state.** Prefer a `Cubit` for simple state, a `Bloc` (event-driven) when there are many distinct triggers or you want an event audit trail.
- **Blocs depend on use cases, not repositories.** Inject use cases through constructor parameters (named for 3+ deps); a use case wraps one repository method and converts exceptions into `Failure` values.
- States are **immutable** and exhaustive (e.g. `initial / loading / loaded / error`). Widgets react via `BlocBuilder`/`BlocListener`/`BlocSelector` — never read mutable fields directly.
- Side effects (navigation, snackbars, dialogs) go through `BlocListener`, not inside `build`. Navigation is `context.push/go` from GoRouter — never `Navigator.push(MaterialPageRoute(...))`.
- Provide page-scoped Blocs at each page's own `BlocProvider(create: (_) => getIt<XBloc>())`. App-wide blocs (`LocaleCubit`, `LanguageCubit`) belong in `AppBlocProviders`.

### Bilingual / Japanese specifics

- Model lesson/vocabulary content so a single schema serves both languages; don't hardcode English assumptions (e.g. word boundaries, romanization, plurals).
- Plan for furigana, JLPT level tagging, and CJK-capable fonts in the theme from the start — retrofitting these is expensive.
- Use Flutter's `flutter_localizations` + ARB files for the **app chrome** (buttons, labels); keep that separate from **learning content** (the words/sentences being taught), which belongs in the data layer.

## Adding a new feature

1. Create `lib/features/<feature>/{data,domain,presentation}/` with the standard subfolders (`data/{datasources,repositories}`, `domain/{entities,repositories,usecases}`, `presentation/{bloc,pages,widgets}`).
2. Define entities and the repository interface in `domain/`. Implement the repository (with at least an in-memory stub) in `data/`.
3. Write one use case per repository method in `domain/usecases/`, each returning `Either<Failure, T>` from `core/utils/failure.dart` (or `Either<Failure, Stream<T>>` via `StreamUseCase`).
4. Build the Bloc/Cubit in `presentation/bloc/` depending only on use cases. Wire its state on `result.fold(...)`.
5. Build the page(s) in `presentation/pages/`. Provide the Bloc with `BlocProvider(create: (_) => getIt<XBloc>())`; use `context.read<LanguageCubit>()` / `context.read<LocaleCubit>()` only for genuinely app-wide blocs.
6. Register the data source, repository, every use case, and the bloc/cubit in `lib/config/di/service_locator.dart`.
7. Add a route constant to `lib/config/router/route_names.dart` and a `GoRoute` to `appRouter`. If the route takes arguments, define a typed `…Args` class next to the others in `app_router.dart` and cast `state.extra!` in the builder.
8. Add tests in `test/features/<feature>/` mirroring `lib/`.

## Conventions

- Keep `flutter analyze` clean — treat lint warnings as errors. Use the standard `flutter_lints` / `package:lints` ruleset via `analysis_options.yaml`.
- Tests live under `test/` mirroring `lib/`. Use `bloc_test` for Bloc logic and `flutter_test` for widget tests.

### Test patterns

- **Bloc/Cubit tests** mock use cases with `mocktail` (not repositories). Stub `when(() => mockUseCase(any())).thenAnswer((_) async => const Right<Failure, T>(value))` — and `registerFallbackValue` for each custom `Params` type in `setUpAll`.
- **Widget tests** that pump a feature page need GetIt set up. Use `setUp(useTestServiceLocator)` from `test/helpers/test_di.dart` — it calls `setupServiceLocator()` and registers a `resetServiceLocator()` tearDown so singletons don't leak between tests.
- **Widget tests** that exercise navigation (any page that calls `context.push/go`) need a GoRouter ancestor. Use `buildTestRouter(home: pageUnderTest, extraRoutes: [...])` from `test/helpers/test_router.dart` to construct a minimal router, then `materialAppRouter(router: router)` to host it. Don't reuse the production `appRouter` in tests — it has the auth redirect.
- Pin `locale: Locale('vi')` and pass `localizationsDelegates`/`supportedLocales` for any test that asserts on localized strings — `materialAppRouter` does this by default.
